## 直した所（commit 92d083f2）
1. **state-deploy.yml**
   - 「いまの main の先端を取る」段（`gh api repos/.../commits/main`）を足し、関門（`HEAD_SHA`）と `actions/checkout@v4` の `ref:` をその sha にした。群れで待つ間に main が進んでも、起こした時の古い commit を配らない。検査を通っていない本体・パネルは、今までどおり check-pass の版へ戻す（作法18）。
   - deploy-pages を三度まで（一度目が落ちたら20秒、二度目も落ちたら60秒おいて出し直し。最後の一度は落ちを隠さない）。environment の url は三つの出力のどれか。
2. **check.yml**
   - 印（check-pass）を進める段を、配信の段（群れの中）から**新しい段 `pass`（群れの外・`needs: [scope, check]`）**へ出した。deploy は `needs: [scope, check, pass]`。群れの待ちは一本だけで、後から札と状態の配信が並ぶと待っていた配信の段は取り下げられる（cancel-in-progress: false でも待ちの側は取り下げ）。取り下げで印が進まないと、通った panel が古い版へ戻されたまま配られ続けるので、先に進めておく。
   - deploy-pages を同じく三度まで。
3. **群れ（concurrency）**：Pages を出すのは check.yml の deploy と state-deploy.yml の deploy の二つだけ（他の workflow に deploy-pages は無い）。どちらも job の単位で `group: pages`・`cancel-in-progress: false` が既にある。**workflow の単位には付けなかった**——check.yml に付けると検査（10〜15分）の間ずっと札と状態の配信が止まり、state-deploy.yml で workflow と job の両方に同じ群れを付けると自分で自分を待って詰まるため。
